Create a GitHub pull request for the current branch following the rules below.

## PR title

- Use **conventional commit** format: `<type>[optional scope]: <description>` (e.g. `feat: add flux capacitor support`)
  - Common types: `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, `ci`, `style`, `perf`, `build`
- Keep under 70 characters
- Use imperative mood
- Do not end with a full stop
- Use British English spelling

## PR description format

### Check for a repository PR template first

Before composing the description, check whether the repository has a pull request template by looking for these paths (in order):

1. `.github/PULL_REQUEST_TEMPLATE.md`
2. `.github/pull_request_template.md`
3. `PULL_REQUEST_TEMPLATE.md`
4. `pull_request_template.md`
5. `docs/pull_request_template.md`

If a template exists, use it as the structure for the PR description. Fill in each section of the template with relevant content derived from the changes. Omit any sections that are not applicable (e.g. remove empty checklist items or headings with no content), but preserve the template's overall structure and headings.

The following rule still applies on top of the template:

- **No agent attribution**: do not mention that the PR was generated by an AI, agent, or tool (e.g. no "Generated with Claude Code" or similar).

### Default format (when no template exists)

If no template is found, use this structure:

```
<one-line summary of the functionality>

## Summary
<bulleted list of key changes>

## Implementation details
<optional — include only if it adds value beyond what the summary and diff already convey>
```

With these rules:

- **One-line summary**: a single sentence at the top describing what the PR delivers, before any headings.
- **Summary section**: a short bulleted list of the key changes. Focus on *what* changed and *why*, not every file touched.
- **Implementation details section**: include this only when there are non-obvious design decisions, trade-offs, or context that a reviewer would benefit from knowing. Do not replay the diff or list every modification — explain the reasoning behind important choices.
- **No test steps section**: do not include a test plan, test steps, or QA checklist.
- **No agent attribution**: do not mention that the PR was generated by an AI, agent, or tool (e.g. no "Generated with Claude Code" or similar).

## Process

1. Run `git status` (never use `-uall`) and `git diff` to review all changes.
2. Check whether the current branch tracks a remote and is up to date.
3. Run `git log` and `git diff <base-branch>...HEAD` to understand the full set of commits being included — not just the latest one.
4. Compose the PR title and description according to the rules above.
5. Push to the remote with `-u` if needed.
6. Create the PR using `gh pr create`.
